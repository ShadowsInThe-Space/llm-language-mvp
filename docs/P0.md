# Implementiertes Sprachprofil p0

## Autorisierte Baseline und Kandidat

```lisp
(spec p0 (fn (params Int Int) (result Int)
  (requires true)
  (ensures (int.eq result (if (int.le (var 1) (var 0)) (var 1) (var 0))))))
```

```lisp
(candidate p0 (body (if (int.le (var 1) (var 0)) (var 1) (var 0))))
```

Dies sind zwei getrennte Eingaben. Im kanonischen Format steht jeweils genau eine Form
auf einer Zeile mit einem Leerzeichen zwischen den Elementen und ohne abschließendes Newline.
Dateien dürfen zusätzlich bedeutungslosen Whitespace enthalten. Kommentare und Strings fehlen.

## Grammatik

```ebnf
spec       = "(" "spec" "p0" fn { fn } ")" ;
fn         = "(" "fn" "(" "params" { type } ")"
             "(" "result" type ")" "(" "requires" expr ")"
             "(" "ensures" expr ")" ")" ;
candidate  = "(" "candidate" "p0" body { body } ")" ;
body       = "(" "body" expr ")" ;
type       = "Int" | "Bool" ;
expr       = integer | "true" | "false" | "result"
           | "(" "var" index ")"
           | "(" "call" index { expr } ")"
           | "(" "let" expr expr ")"
           | "(" "if" expr expr expr ")"
           | "(" "not" expr ")"
           | "(" binary expr expr ")" ;
binary     = "int.add" | "int.sub" | "int.mul" | "int.le" | "int.lt"
           | "int.eq" | "and" | "or" | "bool.eq" ;
```

Integer sind `0`, positive Dezimalzahlen ohne führende Null oder deren Negation.
`-0`, `+1`, Exponenten, Brüche und implizite Konvertierungen werden abgelehnt.
Ein Index ist nichtnegativ und muss im jeweiligen Kontext gültig sein.

## Typ- und Auswertungsregeln

| Ausdruck | Argumente | Ergebnis / Regel |
| --- | --- | --- |
| Integerliteral | — | mathematisches Int |
| true / false | — | Bool, ausdrücklich verschieden von Int |
| int.add / int.sub | Int, Int | exaktes Int |
| int.mul | Int, Int | exaktes Int; mindestens ein syntaktisches Integerliteral |
| int.le / int.lt / int.eq | Int, Int | Bool |
| not | Bool | Bool |
| and / or / bool.eq | Bool, Bool | Bool; beide Operanden werden ausgewertet |
| if | Bool, T, T | T; ausschließlich der gewählte Zweig wird ausgewertet |
| let | S, T unter erweitertem Kontext | T |
| call | Argumente gemäß Signatur | deklarierter Rückgabetyp; Zielindex kleiner als Caller |
| result | nur in ensures | deklarierter Rückgabetyp des öffentlichen Einstiegs |

Parameter stehen links nach rechts; var 0 ist der letzte. Ein let schiebt seinen Wert
nur für den Körper an die Stelle var 0, vorherige Binder steigen dort um eins.
result ist ein separater Slot und verschiebt keine Variablen. Verträge sind aufruffrei.
Jede erreichte Aufrufvorbedingung wird unter der gültigen Einstiegsvorbedingung geprüft.
Die endliche Termstruktur mit streng fallenden Aufrufindizes liefert abstrakte Terminierung.

## Ressourcen und Transport

Defaultlimits: 128 KiB Quelltext, 12000 Syntax-/AST-Knoten, Tiefe 96, 32 Parameter
pro Funktion, 1024 Literalziffern, 8192 Integerbits für konkrete Ausführung,
100000 Arbeitsschritte und 4096 symbolische Verzweigungsschritte. Die symbolische
Darstellung ist exakt und budgetiert. Erschöpfung ist keine Aussage, der Vertrag sei falsch.

JSON transportiert Int als `{"type":"Int","value":"9007199254740993"}` und Bool als
`{"type":"Bool","value":true}`. Duplicate keys und nichtkanonische Werte sind ungültig.
Zertifikatsbrüche sind gekürzte Paare nichtnegativer Zähler- und positiver Nennerstrings.

## Hash- und Zertifikatsbindung

SHA-256 verarbeitet vier nacheinander längengerahmte UTF-8-Felder: Domänenkennung,
Profil `p0`, Checker-Version `cert-v0.1`, kanonischer Inhalt. Jede Länge ist ein
unsigned 64-bit Integer in Big Endian. Baseline und Kandidat haben verschiedene Domänen.
Eigenhashfelder gibt es in diesen Inhalten nicht. Alle Deklarationen, Signaturen,
Verträge, Literale und Körper werden gebunden. Diagnostische Metadaten haben keine Semantik.

Der Checker rekonstruiert die Pflichten aus derselben Baseline und demselben Kandidaten,
prüft Typen und Zweigabdeckung und prüft anschließend jeden rationalen Beleg exakt.
`domains` kann zusätzliche geprüfte Leerheitsbelege enthalten; für den Funktionsbeweis
ist eine nichtleere Domäne nicht erforderlich, für die MVP-Abnahme schon.

## Beweis- und Laufstatus

Verifikation: invalid, unverified, counterexample, proved.
Domäne je Einstieg: domain_nonempty, contract_empty, domain_unknown.
Lauf: returned, input_rejected, resource_exhausted, host_error bzw. noch nicht ausgeführt.
Ein Gegenbeispiel erfüllt die Einstiegsvorbedingung und verletzt die Nachbedingung
oder eine tatsächlich erreichte Aufrufvorbedingung. Es wird konkret nachgerechnet.

## Diagnostikpfade

Lexikalische Parserfehler verwenden `path=[character_offset]`; Unicode-Zeichen werden
gezählt, EOF liegt bei len(source). Grammatikfehler behalten stabile Fehlercodes;
eine vollständige Token-Source-Map gehört nicht zu diesem Parser. Core-Pfade lauten:

- Spec: `[0, fn_index, field, child...]`, field 0=Parameter, 1=Ergebnistyp, 2=requires, 3=ensures.
- Body: `[1, fn_index, child...]`; Kindindizes folgen Expr.args.
- Hosteingabe: `[2, entry, arg]`.
- Separat ausgewerteter Vertrag: `[3, child...]`.

Gegenbeispiele tragen außerdem Verpflichtungs-ID, Baseline- und Kandidatenhash.
